# 設計規格 — 方向框架與共用技術骨架

日期：2026-09-21（開賽日）
狀態：已由使用者核准，進入實作

## 目的

為競品盤點後倖存與待定的三個方向（2、3、6）各做出一套可套用的框架，
並建立一套三方向共用的技術骨架，使賽事當天在聽完現場社企的挑戰陳述後，
能在最短時間內把真實提案者的問題塞進既有形狀，而不是從零開始。

**本規格不選定題目。** 現場優先原則（交接文件第 7 節）仍然凌駕一切：
10:00 出現的真實問題優先於這三個方向中的任何一個。
框架的價值在於**提供形狀與已驗證的證據**，不在於預先決定做什麼。

## 設計依據

三份框架不各自為政，而是同一個模板的三個實例。模板直接由 `AI_CONTEXT.md` 推導：
「Repeated winning patterns」七項與「Build and pitch order」十步。
共用模板使三個方向當天可橫向比較，也使現場提案者能被快速歸位。

## 七格模板（每個方向必填）

| 格 | 內容 | 依據 |
|---|---|---|
| 1 | 一位使用者、一個時刻、一個被卡住的結果 | Build order #1；winning patterns #1、#2 |
| 2 | 現行流程的斷點：最高成本或最高風險的那一步 | Build order #3 |
| 3 | 理想的人類工作流（AI 之前） | Build order #4 |
| 4 | AI 只負責的受限任務（分類／檢索／抽取／摘要／建議／警告 擇一） | Build order #5 |
| 5 | 人類保留決定權的高風險節點 | Winning patterns #6 |
| 6 | 黃金路徑 ＋ 一條低信心／失敗路徑 | Build order #6、#7；winning patterns #7 |
| 7 | 組織拿得走的一個數字 | Winning patterns #5 |

**第 3 格是閘門**：理想的人類工作流沒寫出來之前，不得進入第 4 格。
這是為了阻止「先挑 AI 技術再回頭找問題」，也就是 `AI_CONTEXT.md`「Avoid」清單的第二項。

另附三格賽事用欄位：**付費方**、**碰撞的一句話答案**、**demo 資料來源與誠實邊界**。

## 三個方向的骨幹

- **方向 2 — 二手店進貨端分流**：進貨區工作人員／志工面對一件剛收到的捐贈物，
  卡在「上架／修／纖維回收／退回」的選擇。AI 做分類與去向建議並附信心值，人決定。
  數字為當日省下的處理成本。碰撞對象：Recycle Mate。
- **方向 3 — 社企證據層**：認證負責人在重新認證或投標截止前，卡在同一份證據要重新表述第三次。
  AI 只做既有文件的抽取與對映，不生成主張。數字為一份證據被重用的次數。
  **前置條件**：必須先能回答「Amplify 免費且有學術背書仍因無人採用而關閉，你憑什麼不一樣」。
  答不出則當天不選此方向。
- **方向 6 — WISE 成效申報**：營運主管在向 Outcomes Fund 申報前，卡在彙總數字與申報格式對不上。
  AI 只做彙總與格式對映。數字為申報準備工時。碰撞對象：Social Enterprise Australia 的 shared data system。

## 技術骨架

### 形狀

一個殼、三個可插拔的方向模組，共用同一條管線：

```
輸入 → 受限任務 → 帶來源與信心值的結構化輸出 → 人類確認 → 記錄一個成效數字
```

三個方向的差異只在 prompt 與 schema。殼、信心值處理、低信心分支、成效記錄共用。

### 刻意的限制

- **一次模型呼叫**，不做 RAG、不做 agent、不做 vector database
  —— `AI_CONTEXT.md`「Avoid」明文列出這三項為未驗證問題前不得採用
- **零外部套件**：僅用 Python 標準函式庫。安裝任何相依套件需使用者另行批准；
  賽事當天確定方向後再接真實模型 API
- **模型呼叫層是介面，預設為 stub**：骨架可在無網路、無 API key 的情況下完整跑完黃金路徑，
  這同時就是 demo 備援

### 硬性安全限制（寫進程式介面，不只寫在文件）

方向 6 只能輸出**彙總**結果。骨架在資料結構層強制：
受支持員工的個人層級欄位不得出現在輸出中，且彙總結果低於最小群體規模時必須拒絕輸出。
這條對應交接文件方向 6 的倫理紅線，也對應 `AI_CONTEXT.md`「Avoid」的
「Automated welfare, medical, crisis, or eligibility decisions」。

### 檔案配置

```
skeleton/
  app.py                  stdlib http.server 網頁殼
  core/
    schema.py             輸入／輸出資料結構、信心值、來源、彙總防護
    pipeline.py           共用管線與低信心分支
    model.py              模型呼叫介面 ＋ stub 實作
  directions/
    d2_triage.py          分類 → 去向建議
    d3_evidence.py        抽取 → 對映
    d6_outcomes.py        彙總 → 申報格式
  demo_data/              三組合成樣本
tests/                    stdlib unittest
```

### 驗證

`bin/verify.sh` 的標記區段補上 `python3 -m unittest`，使骨架的失敗成為紅燈。
測試至少涵蓋：低信心分支會觸發、方向 6 的彙總防護會擋下個人層級欄位與過小群體。

## 現場提案者辨識表

獨立一份 `docs/frameworks/onsite-matching-sheet.md`：
列出聽到什麼樣的陳述就對應到哪個框架、哪些陳述代表**不要套**（例如落入已淘汰方向），
以及當現場提案不屬於任何既有框架時，用七格模板現場重建的問法。

## 不做的事

- 不預先選定賽事題目
- 不建立真實模型 API 整合（需使用者批准相依套件，且應在方向確定後才做）
- 不為已淘汰的方向 1、4、5 建立框架
